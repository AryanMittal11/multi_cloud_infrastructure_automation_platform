1Introduction & Core Concept

What cloudweave is, in one paragraph a supervisor can repeat.

cloudweave is a web platform that gives a team one centralized control plane for infrastructure on AWS, Azure, and GCP. Instead of hand-writing Terraform and running it from laptops, a user picks a curated, production-grade template (or draws the architecture on a visual canvas), configures it through schema-driven forms, and ships it through a governed pipeline: plan → policy check → human approval → apply. Everything the platform provisions is then recorded, observable, and costed — resources, dependency topology, and estimated monthly spend — and every meaningful action lands in an immutable audit log.

The design principle underneath the whole product: make the safe path the easy path. Templates ship with security guardrails built in; policy runs before humans review; destructive actions require typed confirmation; credentials never leave the encrypted store.

One-sentence pitch. cloudweave = Terraform's power + a governed, auditable, multi-cloud workflow that a whole team — not just Terraform experts — can use safely.

Scope statement

cloudweave provisions and manages infrastructure; it does not replace your cloud console. It currently targets AWS, Azure, and GCP core services (network, compute, databases, storage) through 12 curated Terraform modules, with a simulation runner for safe demonstrations. The architecture is designed so the simulation layer is the only component that touches the cloud SDK boundary — swapping in live provider execution is a runner-level change, not a redesign.

2The Problem

Why teams doing multi-cloud infrastructure the default way struggle.

Cloud platforms are powerful, but their native tools are provider-specific and expert-oriented. A team that runs workloads on AWS and Azure (and experiments on GCP) faces five compounding problems:

ProblemWhat it looks like in practice
1 · Fragmentation across consolesThree consoles, three IAM models, three billing formats. No single answer to "what do we run and where?"
2 · Terraform expertise bottleneckWriting correct HCL, state handling, and provider pinning is an expert skill. Everyone else either waits or makes risky manual console changes.
3 · Ungoverned changesAnyone with console access can delete a database. There is no plan review, no approval, no record of who did what.
4 · Invisible cost until the billCost appears at month end, per provider, after decisions are already made. Nothing prices a change before it is applied.
5 · No operational memoryResources exist but nobody knows what depends on what, or what a change will break. Tearing down "an idle VM" can kill a database network path.

Existing answers each solve one slice — multi-cloud dashboards (view only), IaC pipelines (expert-only), CSPMs (audit only), FinOps tools (cost only). None give a small team a single governed path from intent to running, observable infrastructure. That is the gap cloudweave occupies.

Templates12 canonical Terraform modules on disk (4 per provider), synced into the catalog with JSON-Schema parameter contracts.

Deployment lifecycle (the spine of the system)

1 · CREATE deployment (DRAFT)→2 · PLAN job → tfstate + diff→ 3 · POLICY evaluation (guardrails)→4 · AWAITING_APPROVAL→ 5 · named approver signs→6 · APPLY → resources recorded→ 7 · Operate: resources / topology / costs→8 · DESTROY (typed confirm)
Key invariants. Credentials are AES-256-GCM encrypted at rest and decrypted only inside the worker; every state transition writes an audit row; DESTROY deployments mark the original deployment's resources destroyed (scoped by project + environment + template) so inventory and cost never lie after teardown.

5What We Built — Five MVPs

Five demonstrable flows, each testable live in under two minutes.

MVP 1 · Multi-cloud governance backbone

Accounts, projects, environments, RBAC

Onboard AWS/Azure/GCP accounts (credentials encrypted, validated live), group work into projects and dev/staging/prod environments each bound to its own account, and role-gate every action (ADMIN governs, DEVELOPER ships, VIEWER reads).

  • Demo path: sign up → onboard a cloud account → create project + 3 environments → observe role gating as VIEWER.
  • Proves: one identity plane over three clouds, least-privilege by construction.
MVP 2 · Curated template catalog

12 hardened Terraform modules with schema contracts

Four modules per provider — VPC/VNet, compute, database, storage — synced from disk with JSON-Schema parameter contracts. Guardrails are inside the modules: private-by-default databases, encrypted storage, deny-by-default security groups.

  • Demo path: Template Catalog → Inspect Schema → see typed parameters and defaults.
  • Proves: paved roads. Users configure; the module carries the security defaults.
MVP 3 · Visual designer → Terraform

Canvas that writes production-ready main.tf

Place network, compute, database, storage nodes on a canvas and wire dependencies; the diagram and the generated Terraform never diverge. Designs save as reusable artifacts and can be handed to the pipeline.

  • Demo path: Saved Designs → open designer → place VPC + EC2 + RDS → draw edges → watch main.tf update live.
  • Proves: visual intent compiles to IaC — no blank-page Terraform.
MVP 4 · Governed pipeline with policy + approvals

Plan → policy → approve → apply, with receipts

The worker runs terraform plan in an isolated runner; a guardrail engine checks encryption, exposure, and CIDR allowlists before a human sees the diff; a named approver signs off; apply records every provisioned resource. Destructive plans require typed confirmation.

  • Demo path: launch AWS EC2 Web Server → configure → plan shows diff + policy results → approve (named, recorded) → apply → resources appear in inventory.
  • Proves: no change reaches the cloud without a plan, a policy verdict, and a human receipt.
MVP 5 · Operate surface: inventory, topology, costs

Recorded resources, dependency graph, cost estimate + optimizer

Every apply records the provisioned resources (grouped by kind, cross-cloud). A topology graph shows network → compute → database blast radius. Cost estimates per project/deployment come from an offline rate card at plan time, and a rule-based advisor suggests concrete optimizations (idle sandboxes, oversized volumes, region arbitrage) with projected savings.

  • Demo path: Resources → Topology → Costs → Optimization advisor (live: $78.40 → $36.45/mo projected).
  • Proves: the platform observes what it provisions — inventory, blast radius, and cost before the bill.

9Limitations & Roadmap

Honest boundaries, and what comes next.

Current limitations (by design)

  • Simulation runner. Applies execute in a sandboxed simulation that produces realistic tfstate, logs, and resource records — ideal for demos and CI, not yet live cloud calls.
  • Module breadth. 12 curated modules (4 per provider) covering network/compute/database/storage; breadth grows by adding modules, not code.
  • Estimates, not bills. Cost figures use an offline rate card; real-time pricing and actual billing ingestion are future work.

10Conclusion

cloudweave demonstrates that a small team can ship a governed multi-cloud platform: a single control plane over AWS, Azure, and GCP where infrastructure is templated, visualized, planned, policy-checked, approved, applied, and operated — with inventory, topology, and cost always current, and every action attributable. The five MVPs each prove one link of that chain, and the extras (audit, sealed credentials, RBAC, safe teardown, cost advisor, portability) turn the chain into a product.

The thesis in one line: make the safe path the easy path — and multi-cloud stops being three consoles and becomes one product.
